## For the architect: CLAUDE.md

The note under "Key patterns" that begins "Tests run `tc` as a
subprocess, or load it as a module" is now short of the code. It
should add:

- Load `tc` or `board/serve.py` only through
  `_root.load_source(name, path)`. It compiles from source and never
  reads or writes a bytecode cache, since Python trusts one by size and
  whole-second mtime alone. A hand-built `SourceFileLoader` or
  `spec_from_file_location` in a test file fails
  `tests/test_no_bytecode.py`.
- The pointer `tests/test_keepalive.py shows how` still holds, but
  `load_tc` in `tests/test_router.py` is the better example: it sets
  TC_ROOT for the load as the note asks, and test_keepalive's does not.
- Every harness child runs with `PYTHONDONTWRITEBYTECODE=1`.

And the Layout block could list `tests/test_no_bytecode.py`: no loader
writes or trusts a bytecode cache (R30).

## Calls I made

- **A new test file.** The work set names `_root.py`, the files with a
  loader and this handoff. Item 3's tests had to live somewhere; a new
  file touches no one else's suite. `tests/test_root.py` was the other
  home, and it is not in the work set either.
- **A source-only loader in place of the flag.** The brief allows "an
  equivalent that never writes a cache". `sys.dont_write_bytecode`
  stops a write and still reads a cache whose header matches, so a
  stale one left by an older run, or by a tool outside the harness,
  would still run. Test 4 proves the difference: with the flag alone
  it is red. The flag is not set around the load at all, since nothing
  then writes: tc and serve.py import the standard library only. If
  either ever imports a sibling file of its own, that import would go
  through the normal machinery and could cache.
